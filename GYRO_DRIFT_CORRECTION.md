## 2. Цветопередача: что проверено

Проверено на камере OS08A10 (`/dev/video0`, 1920×1080):

- фактический формат — **YUYV**, 2 байта на пиксель, кадр 4 147 200 байт;
- ручная конверсия `COLOR_YUV2BGR_YUY2` и штатный путь OpenCV
  (`CAP_PROP_CONVERT_RGB=1`) при **зафиксированных AE/AWB** совпадают:
  средняя абсолютная разница по BGR ≈ **3.4 / 3.7 / 3.2** единицы;
- интерпретация буфера как UYVY даёт «полосы» и неверный цвет — порядок YUYV
  подтверждён;
- `v4l2-ctl --get-fmt-video` вне стрима показывает `RGB4`/`META` и может
  игнорировать `--set-fmt-video=...YUYV`. Ориентироваться на это значение нельзя:
  реальный формат проверяется через `cap.get(CAP_PROP_FOURCC)` и размер буфера.

### Важное наблюдение

Переключение `CAP_PROP_CONVERT_RGB` на живой камере меняет согласование потока
и может изменить экспозицию/баланс белого. Поэтому сравнивать цветовые формулы
можно только при заранее зафиксированных контролах:

```bash
v4l2-ctl -d /dev/video0 \
  -c white_balance_automatic=0 -c white_balance_temperature=5000 \
  -c gain_automatic=0 -c gain=100 \
  -c auto_exposure=0 -c exposure_time_absolute=33
```

### Почему изображение может быть розовым/тёмным

Приложение при каждом запуске делает:

```cpp
system("v4l2-ctl ... -c gain_automatic=0 ...");
system("v4l2-ctl ... -c white_balance_automatic=0 ...");
system("v4l2-ctl ... -c auto_exposure=0 ...");
```

Это отключает автоэкспозицию и автобаланс белого, но **не задаёт** рабочие
значения. В результате остаётся случайная/дефолтная точка (например, маленькая
выдержка и фиксированная температура 5000 K). Отсюда тёмная или цветная картинка.

Рекомендации:

1. Не отключать AE/AWB по умолчанию. Оставить это опцией для борьбы с бросками
   тока (`VS_CAM_NO_AUTO=1`).
2. Если авто-контролы всё же выключаются, задавать рабочие значения
   (`exposure_time_absolute`, `gain`, `white_balance_temperature`).
3. Проверить `sensor_ir_cut_set`: у модуля может отсутствовать ИК-фильтр,
   тогда розовый/фиолетовый оттенок — физика сенсора, а не ошибка конверсии.
4. Для проверки запускать `tools/color_probe.cpp` при неподвижной камере.

## 3. `CMD_GYRO_CORRECTION` (#75)

Источник: **SimpleBGC32 Serial API Protocol Specification**, раздел
`IMU correction and diagnostic → CMD_GYRO_CORRECTION (#75)`, стр. **61**.
Ссылка: <https://www.basecamelectronics.com/files/SimpleBGC_2_6_Serial_Protocol_Specification.pdf>

### 3.1. Назначение

Ручная коррекция нулевого смещения гироскопа (zero bias). Команда не задаёт
угол и не двигает подвес напрямую: она добавляет поправку к нулю датчика, из-за
чего система перестаёт «уводить» ось.

### 3.2. Payload (9 байт)

| Поле | Тип | Размер | Смысл |
|---|---|---|---|
| `IMU_TYPE` | `1u` | 1 | 0 — main IMU, 1 — frame IMU |
| `GYRO_ZERO_CORR[3]` | `2s*3` | 6 | поправки по X, Y, Z, little-endian |
| `GYRO_ZERO_HEADING_CORR` | `2s` | 2 | поправка только по глобальной оси Z (heading) |

Единицы: **0.001 gyro sensor unit** (сырые LSB гироскопа). Диапазон каждого
поля — `int16` (`-32768..32767`). В спецификации физический масштаб LSB не
задан: он зависит от модели гироскопа. Для типового гироскопа SimpleBGC
16.4 LSB/(град/с) это даёт `16400` единиц на 1 град/с — **гипотеза, которую
нужно подтвердить экспериментом**.

### 3.3. Формат кадра

Protocol v1 (проще, поддерживается всеми прошивками):

```
0x3E | CMD=75 | SIZE=9 | (75+9)&0xFF=0x54 | payload[9] | SUM(payload)&0xFF
```

Пример для нулевой поправки:

```
3E 4B 09 54 00 00 00 00 00 00 00 00 00 00
```

Protocol v2 (прошивка 2.68b0+, CRC16):

```
0x24 | CMD=75 | SIZE=9 | 0x54 | payload[9] | CRC16(header+payload, LE)
```

CRC16 — полином `0x8005`, начальное значение 0 (Appendix A спецификации).
Реализация проверена на примере `CMD_BOARD_INFO` из спецификации: `E6 13`.

Ответ на команду — `CMD_CONFIRM (#67)` с `CMD_ID=75`; ошибка — `CMD_ERROR
(#255)`.

### 3.4. Оси и знаки

В спецификации для #75 явно указан порядок **X, Y, Z**. Как эти оси
соответствуют осям подвеса (roll/pitch/yaw), зависит от монтажа IMU и должно
определяться экспериментально. В прототипе по умолчанию:

```
pitch -> X, yaw -> Z, roll -> Y, все знаки +1
```

Все шесть параметров настраиваются:

```bash
--gyro-axis-pitch x|y|z
--gyro-axis-yaw   x|y|z
--gyro-axis-roll  x|y|z
--gyro-sign-pitch +1|-1
--gyro-sign-yaw   +1|-1
--gyro-sign-roll  +1|-1
```

или переменными `VS_GYRO_AXIS_*`, `VS_GYRO_SIGN_*`.

## 4. Алгоритм оценки дрейфа

Вход — уже существующие `dx`, `dy` (пиксели полного кадра) и `da` (радианы)
между соседними кадрами.

1. **Пиксели → углы.** По горизонтальному FOV `fovH`:
   `fx = (W/2)/tan(fovH/2)`, `fy` аналогично.
   `yaw = atan(dx/fx)`, `pitch = atan(dy/fy)`, `roll = da`.
2. **Угловая скорость.** Деление на `dt` между обработанными кадрами.
3. **Выделение дрейфа.** ФНЧ первого порядка с постоянной `tau`:
   `rate += (1-exp(-dt/tau))*quality*(rate_inst-rate)`.
   Медленный уход подвеса проходит, быстрые намеренные движения подавляются.
4. **Достоверность.** `quality = min(1, pts/50) * inlier_ratio` (доля inliers
   RANSAC). Дополнительно сглаживается. При `quality < minConfidence` поправка
   не выдаётся.
5. **Поправка.** `cmd = -rate * scale`, с мёртвой зоной `deadband` и
   ограничением `maxDps`. Ось и знак выбираются конфигурацией.
6. **Отправка.** Не чаще `--gyro-rate` Гц (по умолчанию 20), чтобы не грузить
   UART и не спамить контроллер.

Ограничение: если сцена неподвижна, а подвес медленно и намеренно панорамируют,
алгоритм воспримет это как дрейф. Для полноценного разделения нужна
feedforward-команда управления подвесом или гироскоп.

## 5. Как запускать прототип

```bash
# Только отчёт по дрейфу, без отправки
./build/myapp_modular --source camera --estimate-only --drift-report --duration 30

# Расчёт поправки #75 в dry-run (пакет печатается, порт не открывается)
./build/myapp_modular --source camera --estimate-only --gyro-correction --duration 30

# Реальная отправка (ТОЛЬКО после проверки осей/знаков/масштаба на стенде)
./build/myapp_modular --source camera --estimate-only --gyro-correction \
  --gyro-port /dev/ttyUSB0 --gyro-baud 115200 --gyro-enable --duration 30
```

Полезные параметры:

```bash
--gyro-fov-h 60       # реальный горизонтальный FOV объектива
--gyro-scale 16400    # единиц #75 на 1 град/с (калибруется)
--gyro-max 2.0        # ограничение поправки, град/с
--gyro-tau 2.0        # постоянная времени ФНЧ, с
--gyro-rate 20        # частота отправки, Гц
```

Строка отчёта:

```
[DRIFT] yaw=+0.358 pitch=+0.476 roll=+0.280 deg/s | angle yaw=+0.06 pitch=+0.26 roll=+0.45 deg | conf=0.71 pts=36 | #75=(-7803,-4587,-5872)
```

## 6. Методика экспериментов

### 6.1. Подготовка

- камера на подвесе, сцена — статичный текстурный объект (не пустая стена);
- зафиксировать AE/AWB (см. §2);
- логировать `[DRIFT]`, `[EST]` и отправленные пакеты;
- начинать с `--gyro-correction` без `--gyro-enable` (dry-run).

### 6.2. Идентификация осей и знаков

1. Подать постоянную поправку только по X (`tools/sbgc_correction --send --x N`).
2. Смотреть, по какой оси и в какую сторону меняется дрейф на изображении.
3. Повторить для Y и Z.
4. Заполнить матрицу соответствия: какая ось #75 двигает yaw/pitch/roll и с
   каким знаком.
5. Проверить перекрёстные связи (подача по X не должна заметно менять две
   другие оси).

### 6.3. Масштаб команды

1. Для выбранной оси подать ступеньку `0 → N` (например, 100, 500, 1000,
   2000 единиц).
2. Измерить установившееся изменение угловой скорости по изображению
   (`deg/s`) до и после.
3. Построить зависимость `Δrate = k * N`. Коэффициент `k` даёт масштаб
   `units per deg/s`, а также мёртвую зону и насыщение.
4. Проверить линейность и повторяемость на 3–5 прогонах.

### 6.4. Достоверность

- сравнить `conf` с реальной ошибкой оценки на синтетическом сдвиге/повороте;
- подобрать `minConfidence` и `deadband` так, чтобы шум на статичной сцене не
  давал команду;
- проверить поведение при потере текстуры, размытии, пересвете.

### 6.5. Замкнутый контур

1. Включить коррекцию с малым коэффициентом (например, `--gyro-scale` в 2–5 раз
   меньше оценённого).
2. Убедиться, что знак обратной связи отрицательный (дрейф уменьшается, а не
   растёт).
3. Постепенно увеличивать коэффициент до подавления дрейфа без автоколебаний.
4. Проверить ограничение `--gyro-max` и поведение при потере трекинга.

## 7. Ограничения и что делать дальше

1. **Масштаб 16400 — гипотеза.** Без эксперимента нельзя гарантировать
   физические единицы: спецификация определяет только «0.001 gyro sensor unit».
2. **Оси/знаки зависят от монтажа.** По умолчанию выбрана правдоподобная, но не
   подтверждённая раскладка.
3. **Шум оценки.** На статичной сцене `da` даёт заметный шум; нужны больший
   `tau`, мёртвая зона и/или более устойчивая оценка поворота (например, по
   аффинной матрице с весами inliers).
4. **Медленное намеренное движение** неотличимо от дрейфа без внешней команды.
5. **Безопасность.** Не включать `--gyro-enable` на лётном стенде до проверки
   знаков и пределов. Всегда держать аппаратный/программный лимит и
   watchdog: при потере трекинга поправка должна сбрасываться в 0.
